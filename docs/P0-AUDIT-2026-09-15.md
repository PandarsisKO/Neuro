# P0 Audit — Autonomous Overnight Execution Safety

Date: 2026-09-15
Scope: `EXECUTION-LADDER.md` Stage 1 (L-10 through L-17), reassigned from Codex to Claude for the
duration of Codex's outage ("Codex won't be working until this weekend reset which is 5 days away").
Ruling under audit: CTO ruling §1 — P0 is strictly an AUDIT of the existing autonomous-execution
machinery (jobs, findings, claims, db), not a rebuild. No scenario below produced a rewrite; every fix
is the narrowest change that closes the specific gap found.

This document is the closeout artifact L-17 asks for: one scenario per rung, each landing in exactly
one of three buckets — **pass** (the system already behaved correctly, proved by a new or existing
test), **fixed-at-sha** (a real defect was found and fixed, with the commit that fixed it), or
**documented limitation** (a real gap exists and is recorded, not silently patched over or hidden).
No scenario below is any of the other things this format could hide: an open-ended rewrite, a
guessed fix never run against the real system, or a "probably fine" left unverified.

## Scenario table

| # | Scenario | Outcome | Evidence |
|---|----------|---------|----------|
| L-10 | Autonomous execution must never touch a live database that already fails a full `PRAGMA integrity_check`, and must take a verified backup before proceeding. | **fixed-at-sha** | `db.preflight_autonomous(envelope_id)` added (new function): full live-DB integrity check → refuse and record failure (never cached as blocking) if not clean → else `db.backup()` (online snapshot + its own `PRAGMA integrity_check` on the standalone file) → record success, idempotent per envelope. `release.py doctor()` now reports the last preflight. Also fixed `db.integrity_check()`'s own `ok` computation, which computed and reported `dangling_origin` (a `project_claims.origin_note_id` pointing at a deleted note) but excluded it from the pass/fail boolean. Tests: `tests/test_p0_preflight.py` (4 tests). |
| L-11 | Executing `t4.execute()` twice against the same inputs, and running the resulting jobs twice, must not create duplicate jobs or duplicate work. | **pass** | Proved (not built): `db.create_job`'s `dedupe_key` lookup (`WHERE dedupe_key=? AND status IN (JOB_ACTIVE)`) already prevents a second identical enqueue while the first is still queued/active, and lease-based exactly-once job claiming (`db.claim_job`) already existed and was already tested. Tests: `tests/test_p0_repeated_execution.py` (2 tests) — zero new jobs, zero new notes/claims/usage rows on a second identical execute, both when the first job already ran and when it's still queued. |
| L-12 | A project's governing inputs (brief, source content) change WHILE a `suggest_findings` job is mid-flight; the job must not write stale-tagged results, and must not be marked a permanent failure. | **fixed-at-sha** `57f3fc7` | `findings.suggest_for_source()`'s pre-existing `_inputs_current()` guard already refused to write stale results — correct — but raised a bare `RuntimeError` that `jobs.execute()`'s `TRANSIENT`-regex retry classification doesn't match, so the job was marked terminally `failed` despite its own message promising "kept for retry." `suggest_for_project()`'s per-source `except` then compounded this by swallowing the same exception as an ordinary per-source failure. Fixed: raise `jobs.Yield` (the existing safe-boundary-requeue mechanism) at all 3 check sites, and re-raise it through `suggest_for_project()` instead of catching it. Test: `tests/test_p0_governing_input_change.py`, real `create_job → claim_job → jobs.execute()` path with a concurrent brief edit. |
| L-13 | A worker crashes mid-`suggest_findings`, after some windows' provider calls are durably persisted but before the source's analysis is complete; restart must not re-pay for the completed windows or lose them. | **pass** | Proved via a new test closing a real *coverage* gap (not a production bug): two pre-existing tests each proved half the claim (`test_s46_r4_durable_units.py`'s window-durability test never touches the real `usage` table; `test_indestructible.py`'s crash-matrix test only covers a whole-source crash after every window already completed). `tests/test_p0_restart_retry.py` combines real usage recording + a real job-level restart (`crashkit.Sim`) + a genuine partial multi-window crash (windows forced sequential via `concurrency.limit_for`, since the default thread pool lets both fake-AI calls land before either reaches the crash point). |
| L-14 | A daily budget wall (or provider outage) is hit mid-project, partway through a multi-source `suggest_findings` job; the remaining sources must resume correctly, once, without racing the wait that caused the pause. | **fixed-at-sha** `9c85f40` | `suggest_for_project()`'s `BudgetPaused`/`ProviderUnavailable` handling created a SEPARATE fresh job for the remaining sources with no wait gating at all (`not_before=None`, immediately claimable) — while `jobs.execute()` ALSO correctly requeued the original job (full source list, proper `wait_reason='budget'`/`not_before` or provider-wait park). The fresh job raced straight past the very wait it was created to respect, and left two jobs covering the same remaining source(s). Confirmed live with a throwaway probe script before fixing. Fixed by folding these two exception types into the same re-raise-and-let-jobs.execute()-handle-it pattern as L-12's `Yield` fix. Test: `tests/test_p0_budget_exhaustion.py`. |
| L-15 | No autonomous code path (`suggest_findings`, `extract_claims`, harvest, `_after_done`, or anything T4/T5 can reach) may ever promote a Claim to `accepted` or `rejected` — only a user-driven API route may. | **pass** | Two independent proofs, no violation found: a static grep of every `.py` under `neurosearch/` for `claims.set_status(`/`set_status(` call sites (only `claims.py`'s own definition, `api.py`'s direct route, and `claims_view.bulk_status` — both API surfaces reachable only from `require_auth`-gated POST routes); and a dynamic run of the real harvest/assess/map pipeline (`claims.ensure()` against `test_k6_claims.py`'s proven multi-claim G5 acceptance fixture) asserting every resulting Claim's status is `proposed` or `superseded` (the one legitimate autonomous transition — dedup/merge of a still-proposed duplicate, itself gated `AND status='proposed'` so it can never touch an already-accepted Claim). Test: `tests/test_p0_promotion_boundary.py`. |
| L-16 | Several `suggest_findings` jobs for the same project complete within the same second (T4's batched executor makes this routine); concurrent `_after_done()` → `claims.harvest()` calls must not raise, duplicate a Claim, or silently lose a note. | **fixed-at-sha** `aef8d4a` | The pre-existing per-project harvest lock (from a 2026-09-14 fix) coalesced: a caller that found the lock held would wait for release and return a no-op, trusting the in-flight call's note scan already covered it. That assumption is false whenever the waiter's own note lands in `project_notes` AFTER the in-flight call's scan snapshot but before the waiter's own `harvest()` call — the note is then never scanned by anyone. A new test (8 real job completions across 4 threads, driving the actual `_after_done()` path rather than calling `harvest()` directly) reproduced this on its FIRST run: roughly 1 in 10, a note was lost permanently and silently (`_after_done()` swallows harvest's exceptions; nothing else retries). Fixed by removing the coalesce — every caller does its own real scan once it holds the lock. 30 consecutive green runs after the fix (gate asked for 20). Test: `tests/test_p0_concurrent_completion.py`. |

## Summary

- 7 scenarios audited (L-10 through L-16); L-17 (this document) closes the set.
- 4 real defects found and fixed: L-10 (`dangling_origin` excluded from `integrity_check`'s own pass/fail),
  L-12 (stale-input `RuntimeError` not retried despite promising to be), L-14 (un-gated duplicate job racing
  past a budget/provider pause), L-16 (harvest coalescing silently losing a note under real concurrency).
- 3 scenarios where the system already behaved correctly and a gap was in test *coverage*, not behavior:
  L-11, L-13, L-15.
- 0 documented limitations — every scenario in scope resolved to pass or fixed; none were set aside as an
  accepted, unfixed gap.
- 0 open-ended rewrites. Every fix is the smallest change that closes its specific gap: a re-raise instead
  of a swallow (L-12, L-14), a boolean computation correction (L-10), a lock-coalescing removal (L-16).
- New test files added this stage: `test_p0_preflight.py`, `test_p0_repeated_execution.py`,
  `test_p0_governing_input_change.py`, `test_p0_restart_retry.py`, `test_p0_budget_exhaustion.py`,
  `test_p0_promotion_boundary.py`, `test_p0_concurrent_completion.py`.
- Full suite at closeout: 1499 passed, 0 failed. `repo-check: PASS`.
- Every commit in this stage carries the two-commit discipline (implementation + test, then a separate
  ladder-status/HANDOFF checkpoint commit) — see `git log` for `L-10` through `L-16` prefixed commits, and
  `HANDOFF.md`'s dated sections for the same findings in narrative form.

## What this audit does not cover

P0 was scoped to autonomous-execution safety around the jobs/findings/claims/db machinery specifically.
It does not cover: UI-facing behavior, T4's economic/quality judgment (source relevance, kept-rate — that's
Stage 2, separately gated on Kyle's review), the scheduler surface itself beyond what L-11/L-14 touch
(Stage 3's `not_before` productization and macOS power-assertion testing are separate, later rungs), or
anything downstream of a Claim once it reaches `accepted` (out of scope by definition — L-15 proves
autonomous code can't reach that state at all).
